# 講座の課題PRを作成する

## 目的と起動条件

利用者が終えた回の作業を、内容を確認できるPRとして自分のforkに残す。普段の演習は利用者自身が実行し、終了時のGit操作をこのスキルに任せる運用を支える。

- `$lecture-pr` の呼び出し、またはコミット・push・PR作成を任せる明確な依頼を受けて実行する。課題の完了確認や手順の相談だけではGitHubを変更しない。
- 依頼に含まれるコミット・push・PR作成は、手順ごとに許可を取り直さず進める。環境の実行権限は別途守る。
- このスキルの終点はPRの作成または更新。マージ、auto-mergeの有効化、ブランチ削除、mainへの直接pushは行わない。利用者がマージも依頼した場合は、その操作がこのスキルとは別の依頼であることを明示する。

## 1. 対象回と作業内容を確認する

- 作業先の `AGENTS.md`、対象回の `lectures/NN/problem.md` と `answer.md` を読み、依頼された範囲の完了状況を確認する。
- 対象回は利用者の指定、会話、ブランチ、変更ファイルから特定する。複数の回が候補に残る場合だけ、どの回をPRにするか聞く。
- `git status --short --branch`、差分、未追跡ファイル、履歴、remoteを確認する。既存のローカル変更・ステージ済み変更も、対象回に属するか確かめる。
- 今回に関係するファイルを選ぶ。別の回の変更や共通設定の未確定な変更は勝手に含めない。記録の不足は保存済みの事実で補い、実APIの演習を追加実行したり結果を作ったりしない。

## 2. PRの宛先とブランチを確定する

- 利用可能であればGitHub CLI `gh` を使い、ログイン状態と、push先リポジトリの所有者・名前を確認する。未設定なら、準備できた内容と必要なログイン手順を伝える。
- この講座では、自分のfork内の `作業ブランチ → main` が提出用PRの宛先。remoteとGitHubのリポジトリ情報を照合し、講座本家へ誤ってPRを出さない。宛先が特定できない場合はGitHubを変更する前に確認する。
- `gh` のPR操作には `--repo OWNER/REPO`、`--base main`、`--head 作業ブランチ` を明示する。コマンドの既定リポジトリに任せない。
- リモートの最新状態を取得し、baseとの差分を確認する。対象回の既存ブランチ（例：`le06`）を使い、main上の未コミット作業なら、内容を保ったまま適切な作業ブランチを作る。
- ブランチ切り替えで対象外の変更に干渉する場合は、変更を消したり自動で混ぜたりしない。作業を保てる方法を選び、それが決められない場合は具体的な状態を伝えて相談する。
- すでにmainへ統合済みで新しい差分がない場合は、空のPRを作らず、その事実を報告して終了する。

## 3. 検証してコミット・pushする

- 既存のテスト結果と現在の差分を確認し、必要な関連テストを実行する。通常はAPIを使わないテストを選ぶ。文書だけの変更なら内容・リンク・差分の確認でよい。
- 新しい変更、失敗、未解決事項がなければ、すでに成功した確認を繰り返さない。
- 既知の無関係な失敗と今回の変更による失敗を分ける。今回の範囲内で修正できる問題は修正し、必要な確認をやり直す。未解決事項が残る場合は理由をPR本文に書き、Draftとして作成する。
- `git diff --check` と、実際にコミットする差分を確認する。APIキー・`.env`・個人用ログなど、提出対象外の情報を含めない。
- ファイルを明示してステージする。すでにステージされた対象外の変更があれば、その状態を保つ方法を選び、まとめてコミットしない。
- 対象の変更がある場合だけ、日本語で内容が分かるコミットを作り、作業ブランチをpushする。未pushの既存コミットも対象回の内容か確認する。force-pushや公開済みコミットの書き換えは通常の手順に含めない。

## 4. PRを作成または更新する

- 同じ宛先・base・headのopen PRを探す。既存PRがあれば、それを更新して重複作成を避ける。閉じたPRを勝手に再開しない。
- タイトル例：`第6回：演習と基礎の宿題`。実際に取り組んだレベルと最終的な変更内容に合わせる。
- 本文は最終差分と記録から日本語で作成し、次を簡潔に含める。
  - 取り組んだ内容と、変更によってできるようになったこと。
  - 主な結果と、`lectures/NN/answer.md` などの記録先。
  - 実施したテスト・実行確認と、その結果。
  - AIが代行した実装・実行・ラベル付け、および残る制約があればその範囲。
- 未実施の確認を成功扱いにせず、単発の測定を一般的な性能改善と断定しない。
- CLIで複数行の本文を渡すときは、一時ファイルに正確な本文を書き、`--body-file` を使う。
- PR操作が通信エラーになった場合は、現在のPR状態を読み直してから再試行する。宛先や権限の問題を推測して別のリポジトリへ送らない。

## 5. 作成結果を確認して終了する

- GitHub上のPRのURL、宛先リポジトリ、base、head、open状態を確認する。Draftの場合もその状態を確認する。
- PRのURL、コミット・pushの結果、実施した確認、現在ブランチ、未コミット変更の有無を日本語で伝える。
- マージ待ちであることと、講座の提出フォームへの送信は別であることを明記する。作業ブランチを維持し、利用者がPRを確認できる状態で終了する。
