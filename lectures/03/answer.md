## 演習

### 素のLLMとエージェントの回答の違い

同じモデル（`gemini-3.5-flash-lite`）で、同じ質問を `app.ask` と `app.agent` に送って比較した。

```bash
uv run python -m app.ask "AIE2026の講座の宿題にある「3レベル」とは何ですか？"
uv run python -m app.agent "AIE2026の講座の宿題にある「3レベル」とは何ですか？"
```

| 比較点 | 素のLLM（app.ask） | エージェント（app.agent） |
|---|---|---|
| 3レベルの名称 | 基礎・応用・発展という一般的な構成例を挙げた | 講座の定義に沿って、基礎・実装・発展と答えた |
| 完了条件 | 条件は不明として確認を促しつつ、「大抵はレベル1〜2が必須」という一般論も述べた | どれか1つに取り組めば、その回の宿題は完了すると答えた |
| 回答の特徴 | 講座の名称や課題の内容を推測し、一般的な説明を長く述べた | 講座固有のルールを具体的に説明し、関連する回として第1回を示した |

エージェントの説明は、用語集の `homework-levels` にある内容と一致していた。同じモデルでも、与える指示や利用できるツールによって回答が変わることを確認した。この質問の実行には `--trace` を付けていないため、実際の検索の引数や呼び出し回数は記録していない。

### ツール呼び出しとLLMの呼び出し回数

```bash
uv run python -m app.agent --trace "LoRAとQLoRAの違いは？"
```

次の2件のツール呼び出しが表示された。

```text
[tool call] search_glossary({'query': 'LoRA'})
[tool call] search_glossary({'query': 'QLoRA'})
```

`requests=2`、`tool_calls=2` だった。1回目のLLM応答で2つの検索を要求し、Python側で検索して結果を返した後、2回目のLLM応答で最終回答を作っていた。ツールの呼び出し回数とLLMの呼び出し回数は、必ずしも1対1ではない。

回答では、LoRAは元の重みを固定して小さな行列だけを学習する手法、QLoRAはベースモデルを量子化してメモリを節約したうえでLoRAを行う手法と説明していた。末尾には「関係する回：第2回」があった。用語を1つずつ検索することと、関連する回を表示することが、指示どおりに行われていた。

### 追加したツールとdocstring

`app/tools.py` に `make_quiz(lecture: int) -> str` を追加した。用語集から指定された回の用語を集め、`random.choice` で1つ選び、問題を `question`、定義を `answer` とするJSON文字列を返す。該当する用語がない場合は、「第N回の用語は見つかりませんでした。」という案内を返すようにした。

docstringには、機能、使用する場面、引数の意味を書いた。

```text
指定した回の用語集から確認問題を1問作り、問題と答えを返す。

「第2回の確認問題を出して」のように、復習のための問題を
求められたときに使う。lectureには対象の回を整数で指定する。
```

`app/agent.py` に `agent.tool_plain(tools.make_quiz)` を追加して登録した。`--list-tools` ではツールが3個になり、`make_quiz` の説明文と、`lecture` が整数であることを確認した。

```bash
uv run python -m app.agent --trace "第2回の内容から確認問題を1問出して"
```

実行すると、`make_quiz({'lecture': 2})` が呼ばれ、QLoRAについての問題と答えが返った。最終回答には「『QLoRA』とはどのような手法ですか？」という問題と「関連する回：第2回」が表示され、答えそのものは表示されなかった。この実行は `requests=2`、`tool_calls=1` だった。

ツールは問題と答えの両方を返しているが、LLMはその結果をそのまま表示するのではなく、利用者向けの出題文を作っていることが分かった。

#### やったこと

変更前の説明文：

```text
答える前に使うこと。query には調べたい用語を1つだけ入れる（例: "LoRA"）。
```

変更後の説明文：

```text
答える前に使うこと。複数の用語を比較するときは、query にまとめて入れる（例: "LoRA QLoRA"）。
```

比較元には演習で実行した結果を使い、変更後は次のコマンドを実行した。モデルはどちらも `gemini-3.5-flash-lite` だった。

```bash

```

#### 結果

| ツール呼び出し回数（tool_calls） | 2回 | 1回 |
| LLM呼び出し回数（requests） | 2回 | 2回 |

#### 気づき・疑問

ツールの処理を変えなくても、docstringの指示に沿って、LLMが渡す引数とツールの呼び出し回数が変わることを観察できた。docstringは人が読む説明であると同時に、LLMが道具の使い方を判断するための情報でもあると分かった。

ツール呼び出しは2回から1回になったが、LLM呼び出しは2回のままだった。変更前も1回目のLLM応答で2つの検索を要求し、検索結果を受け取った後の2回目で回答していたためである。ツール呼び出しが減ったことだけから、LLM呼び出し回数や応答時間も減るとはいえない。

検索の呼び方を変えても、検索処理自体が複数用語専用の処理に変わるわけではない。traceではツールの返り値が途中で省略されているため、今回の表示だけではLoRAとQLoRAの両方の定義が返ったかまでは確認できなかった。最終回答に両方の説明があることと、両方の定義を検索で取得できたことは分けて考える必要がある。

比較元は `make_quiz` を追加する前の演習結果なので、説明文に加えて登録ツール数も異なる。また、各条件1回ずつの実行である。このため、観察された変化が説明文だけによるものだと厳密には断定できない。より条件をそろえて確かめるなら、3個のツールを登録したままdocstringだけを戻した場合と変更した場合を比較する方法が考えられるが、今回は追加実行していない。

### 実装：承認を挟んで学習記録を保存する

#### やったこと

`save_learning_log(topic: str, note: str) -> str` を作り、利用者の承認を得た場合だけ、学習した内容をリポジトリ直下の `learning_log/` に保存するようにした。実装はCodexに依頼し、Geminiを使う動作確認と承認・拒否の入力は自分で行った。

- `app/tools.py`：テーマ（topic）、学習内容（note）、保存日時（saved_at）をJSON形式で保存する関数を追加した。フォルダがなければ作成し、UUIDを使ったファイル名と新規作成モードで、既存ファイルの上書きを避けた。
- `app/agent.py`：`requires_approval=True` で登録し、`output_type` に `DeferredToolRequests` を追加した。保存要求が来たら保存先と引数を表示し、`y` または `yes` で承認、それ以外は拒否する。Enterだけの場合や入力が終了した場合も承認しない。
- 再開処理：呼び出しIDごとの承認結果を `DeferredToolResults` に入れ、それまでの会話履歴（`result.all_messages()`）と一緒に `run_sync` に渡す。承認された場合に保存関数が実行され、拒否された場合は実行されず、その結果を受け取ったLLMが最終回答を作る。

ここでいう学習記録は、人が勉強した内容のメモであり、LLMの重みを更新するための学習処理ではない。`learning_log/` は既存の `.gitignore` の対象なので、個人の記録は通常のGit操作ではコミットされない。

#### 結果

次の依頼を、同じモデル（`gemini-3.5-flash-lite`）で2回実行し、1回目は `y`、2回目は `n` を入力した。

```bash
uv run python -m app.agent --trace "テーマはLoRA、内容は「元 の重みを固定し、小さな行列だけを学習する」です。この内容を学習記録として保存してください。"
```

どちらも最初に `search_glossary({'query': 'LoRA'})` が呼ばれ、保存前には `save_learning_log` の引数が表示されて入力待ちになった。

| 確認項目 | 承認した場合 | 拒否した場合 |
|---|---|---|
| 入力 | `y` | `n` |
| 確認画面の表示 | 「承認しました。」 | 「拒否しました。この処理は実行しません。」 |
| save_learning_logの返り値 | 「学習記録を保存しました：ddd2f8e9794c4dc8918708bb94d2f69f.json」 | `The tool call was denied.` |
| LLM呼び出し回数（requests） | 3回 | 3回 |
| usageに表示されたtool_calls | 2 | 1 |
| 最終回答 | 学習記録を保存したと案内した | 「学習内容の記録に失敗してしまいました」と説明した |

承認時は、`learning_log/ddd2f8e9794c4dc8918708bb94d2f69f.json` が実際に存在し、テーマが「LoRA」、内容が「元の重みを固定し、小さな行列だけを学習する手法」、保存日時が入っていることをCodexが確認した。

拒否時にもtraceには `save_learning_log` の呼び出し要求が表示されたが、返り値は拒否を示していた。呼び出し要求があることと、保存関数が実際に実行されることは異なる。

APIを呼ばないテストでは、一時フォルダを使って、承認前には保存されないこと、`y` で承認した場合だけJSONが1件作られること、`n`・空入力・入力終了では保存されないことを確認した。Codexが実行したエージェントとツールの関連テストは13件すべて成功した。第2回のデータ不整合については、演習欄に記載したとおり未修正であり、全体テストがすべて通ったという意味ではない。

#### 気づき・疑問

保存の確認は「実行前に確認して」とLLMに文章で頼むだけでなく、`requires_approval=True` によってPython側で実行を止める仕組みとして実装した。LLMが保存を要求しても、その時点ではファイルが作られず、利用者が内容を見て判断できることが重要だと分かった。

利用者が指定した文章は、そのまま保存関数に渡るとは限らない。今回もLLMは空白を整え、「手法」や句点を加えて引数を作っていた。承認画面で実際の保存内容を表示することで、何が保存されるかを確認できた。

拒否時は仕組みとして正常に保存を止められたが、LLMは「記録に失敗」と表現していた。利用者が意図して拒否したことと、エラーで保存できなかったことは別なので、「保存はキャンセルされました」と案内する方が適切だと考えた。今後の改善点として、拒否結果の説明や指示文を見直す余地がある。今回は表示の課題として記録し、追加修正はしていない。

承認機構が正しく動くことと、LLMの最終的な説明が適切であることは、分けて確認する必要があると分かった。

### 発展(b)：Piの実行と、自作エージェントとの比較

#### 実行環境とやったこと

Mac上のVS CodeのターミナルでPiを動かした。環境準備はCodexに依頼し、Node.jsを `v22.23.5` に更新して、Pi `1.5.2` をインストールした。PiではGoogleのAPIキーを設定し、演習と同じ `gemini-3.5-flash-lite` を選択した。

まず、Piに次の依頼を送った。

```text
app/agent.py と app/tools.py を読んで、この学習支援エージェントの仕組みを説明してください。ファイルは変更しないでください。
```

Piは、モデル・ループ・ツールという構成、各関数の役割、docstringと型ヒント、ツールの登録、保存前の承認処理について説明した。特に、自分が追加した `make_quiz` と `save_learning_log`、`requires_approval=True` の設定も説明に含まれていた。

次に、Piに自分の `app/agent.py` の `INSTRUCTIONS` と、インストール済みPiのシステムプロンプト構築コードを比較するよう依頼した。比較したファイルは、次の場所にある `dist/core/system-prompt.js` である。

```text
~/.nvm/versions/node/v22.23.5/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/system-prompt.js
```

教材が示す[公開ソースのsystem-prompt.ts](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/system-prompt.ts)に対応する、インストール済みバージョンのJavaScriptを確認した。公開リポジトリの最新版とインストール済みバージョンでは内容が変わる可能性があるため、今回の比較対象はPi 1.5.2のコードとした。Piの説明に加え、Codexでもこのファイルを読んで内容を確認し、比較と考察を整理した。

#### 比較結果：何が違うのか

最も大きな違いは、任されている仕事と、使える道具だった。どちらも今回は同じGeminiモデルを使ったが、役割とツールが異なるため、提供する機能も異なる。

| 観点 | 自作の学習支援エージェント | Pi |
|---|---|---|
| 役割 | AIE2026の受講者の勉強を手伝う | ファイルの調査、コマンド実行、コード編集を手伝う |
| 道具 | 用語検索、講義要約、確認問題作成、学習記録の保存 | 標準のツールはread・bash・edit・write |
| 指示の例 | 用語集を確認する、宿題はヒントに留める、関連する回を示す | 簡潔に答える、ファイルパスを明示する、利用可能なツールの使用指針に従う |
| 指示の用意の仕方 | 講座用の基本指示をINSTRUCTIONSに書き、登録した関数のdocstringや引数の情報も渡す | 基本指示に、選択されたツールの説明・使用指針、プロジェクトの指示、スキル、作業ディレクトリなどを組み合わせる |

例えば「確認問題を作る機能を追加して」と依頼した場合、自作エージェントには任意のPythonファイルを編集するツールがない。登録済みの `make_quiz` を使って出題することはできるが、コードを編集して新機能を追加する操作は提供していない。Piはファイルを読んだり編集したりする道具を持つため、開発作業を進められる設計になっている。ただし、今回Piに依頼したのは説明と比較であり、コードの編集やテスト実行をPiに行わせたわけではない。

日本語で役割を変更するだけでは、実行できる操作は増えない。必要な処理を行う道具を用意し、それをLLMに使える形で渡す必要があると理解した。

#### Piの説明に補足した点

Piの比較結果には、自作エージェントは静的な指示文、Piは動的な指示文という説明があった。ただし、自作エージェントもLLMに渡す情報が `INSTRUCTIONS` だけで固定されているわけではない。ツールの説明や引数の情報も渡しており、基礎編ではdocstringを変えることで検索の呼び方が変わった。

また、Piもすべての指示を動的に作り出すわけではない。基本の役割や「簡潔に答える」「ファイルパスを明示する」という固定の指示があり、標準ツール名もコード内にある。それらに環境や設定に応じた情報を追加している。静的か動的かの二択で区別するより、何を共通の指示とし、何を状況に応じて追加するかという設計の違いとして捉えた。

#### 自作エージェントの実用上のメリット

自作する価値は、特定の利用者が繰り返し行う仕事を、決まったルールと道具で利用できる形にすることだと整理した。今回なら、利用者が毎回「講座の用語集を調べて、宿題はヒントにして、関連する回も示して」と説明せずに、講座向けの支援を受けられるように設計できる。

| 利用場面 | 自作エージェントで提供できること |
|---|---|
| 講座について質問する | 講座専用の用語集や講義要点を調べる |
| 復習する | 対象の回を指定して、用語集に基づく確認問題を出す |
| 勉強した内容を残す | 内容を確認してから、決まった保存先と形式で記録する |

また、登録するツールを選ぶことで、提供する操作を講座に必要な機能に絞れる。今のエージェントには、自由にコマンドを実行したり任意のファイルを編集したりするツールを渡していない。ただし、ツールを絞ることと、回答内容が必ず講座の範囲に収まることは別であり、回答の評価は引き続き必要である。

今後、受講者向けの画面を作れば、同じルールや機能を多くの受講者に提供し、共通の改善を反映する講座専用サービスとして活用できると考えた。今回実装したのはCLIで使う機能までで、画面の作成や複数利用者への提供は行っていない。

#### 気づき・疑問

LLMが同じでも、役割を示す指示、渡す情報、実行できる道具、処理を進めるプログラムによって、利用者に提供できるものが変わることが分かった。今回の比較は目的や設計の違いを調べたものであり、Piと自作エージェントの回答品質や性能の優劣を測る実験ではない。

特に、日本語による指示とプログラムによる制御を区別することが重要だった。「宿題の答えを直接書かない」はLLMへの指示なので、守られているか評価する必要がある。一方、「保存は承認後だけ」はPython側で処理を止める仕組みにして、テストでも確認できる。指示文だけでなく、道具と制御の組み合わせまで含めてエージェントを設計する必要があると理解した。
